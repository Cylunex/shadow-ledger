# 产品边界

## 1. 正式定位

Shadow Ledger 是以消费为中心的个人收支记录与规划系统。它用尽可能低的录入成本回答：

- 最近收了、花了或退了多少；
- 买了什么、在哪里消费、体验如何；
- 哪些订阅或周期事项即将发生；
- 过去的频率和偏好对未来有什么提示。

它关注结果型事实，不要求用户说明钱来自哪个账户，也不试图恢复完整支付链路。

## 2. 三层边界

```text
Money Log
└── 最终金额事实：收入、支出、退款

Consumption
└── 消费语义：场景、商家、渠道、商品/菜品、评价与原始凭证

Planning & Insights
└── 未来意图、周期承诺、提醒、统计以及后续可重建预测
```

三层属于同一个服务和数据库，但保留不同语义。金额分类服务于统计和简单预算；消费场景与
内容分类服务于行为理解，二者不能合并为一个字段。

## 3. v1 范围

### 必须完成

- 金额记录：支出、收入、退款，以及可选的轻量支付方式标签（ADR 0008）；
- 消费记录与可选明细；
- 金额未知的消费草稿，以及后续补金额；
- 商家、渠道、商品/菜品身份与原始文本保留；
- 手工快速录入和自然语言解析合同；
- 小票、订单截图进入 Asset 后生成待确认草稿；
- 时间线、搜索、月度汇总、分类和消费频率统计；
- 可选的月度总额或分类消费目标，不做信封预算和余额结转；
- 想买、想吃和一般消费计划；
- 订阅、会员、固定支出/收入等周期承诺；
- 到期提醒和“由计划生成草稿”，不自动确认；
- 用户显式开始/结束的 UseCycle，不把购买解释为开始使用或库存；
- 可解释、确定性、可回算的周期事项、复购间隔和使用周期预测；
- 最小披露 stdio MCP 读取与可选 money-only 草稿；
- Nexus 隐藏 Review 在同一待确认草稿中保留明确提供的消费语义与 `shadow://` 证据引用；
- 结构化 Webhook 和受控导入目录抓单，幂等保存原文且只创建草稿；
- JSON/CSV 导入导出，以及受支持平台的 Markdown 账单草稿导入；
- Platform 原生 OIDC、服务鉴权和 Asset 引用；
- Health、Travel、Foliant 的不透明引用合同。

### 明确推迟

- 机器学习 Forecast、个性化模型训练与自动消费建议；
- MCP/Agent 正式入账、导出与资金执行；
- 邮件收据自动接入和电商/外卖平台抓单；
- 条码外部数据库同步；
- 高级预算、家庭多人协作和公共分享。

### 明确不做

- Account、银行账号、银行卡余额和转账；
- Posting、借贷方向、复式记账、对账和账单核销；
- PaymentAllocation 和多支付方式分摊；
- 优惠、税费、配送费等强制对平；
- 信用卡应还、借贷、资产负债表和净资产真相；
- 库存数量、批次、入库出库和自动补货；
- 实际饮食摄入、营养计算和健康因果分析；
- 证券持仓、行情、策略与交易决策。

## 4. 核心原则

1. 金额优先，快速记录只要求金额和可选描述。
2. `MoneyEntry.amount` 是最终金额唯一真相，始终使用正数，由类型决定汇总方向。
3. 消费明细是内容说明，不要求与最终金额对平。
4. 金额、消费语义和未来计划是不同事实，不能互相冒充。
5. AI/OCR 只产生草稿和身份建议，不能直接产生已确认事实或不可逆合并。
6. 周期承诺只产生提醒或草稿，用户确认后才成为实际记录。
7. 原始文本与原始解析结果必须保留；规范化只能新增关联，不能覆盖来源。
8. 购买、实际使用和实际摄入是三个不同事实。
9. 文件生命周期归 Asset，跨服务引用只使用不透明 `shadow://` URI。
10. 预测是可重新计算的建议，不是事实来源。
11. Agent 首期只有最小披露读取和可撤销草案；正式确认仍由 Ledger 用户会话完成。

## 5. 术语

| 术语 | 定义 |
|---|---|
| Ledger Record | 一次用户可见记录的内部聚合根，持有唯一状态 |
| Money Entry | 收入、支出或退款的最终金额事实 |
| Consumption Event | 一次消费发生了什么 |
| Consumption Line | 可选的商品、菜品、饮料或服务内容 |
| Capture Source | 手工、文本、截图、CSV 等数据从哪里来 |
| Merchant | 实际提供商品或服务的一方 |
| Channel | 下单或发现渠道，例如电商、外卖平台 |
| Item Identity | 多次记录中“是不是同一个东西”的规范身份 |
| Recurring Commitment | 用户明确知道会周期发生的事项 |
| Spending Intent | 尚未发生的想买、想吃或计划消费 |
| Budget Target | 可选的月度总额或分类目标，不表示账户资金 |
| Forecast | 根据历史计算的可过期建议 |
| Use Cycle | 用户明确声明的一段实际使用过程，不是库存或购买的自动推断 |

## 6. 与其他 Shadow 项目的边界

| 项目 | 它拥有的事实 | Ledger 的关系 |
|---|---|---|
| Platform | 身份、应用目录、Agent/服务合同 | Ledger 是独立 OIDC client 和业务服务 |
| Asset | 小票、截图、发票、商品照片的文件生命周期 | Ledger 保存 `asset_id` 和消费语义 |
| Health | 实际摄入、份量、营养、健康影响 | Ledger 可建议生成 Health 草稿，不自动写摄入 |
| Travel | Place、Visit、Trip、路线和经历 | Ledger 引用地点/到访并统计相关消费 |
| Foliant | 证券持仓、行情、投研和策略 | Ledger 只读取明确导出的估值/现金流摘要 |
| Garden | 对外发布的内容 | Ledger 保存私人消费与评价，不自动公开 |
| Archive | 长期资料、说明书、研究与检索 | Ledger 只记录消费；长期材料由 Archive 引用 Asset |

关键等式：

```text
MoneyEntry       ≠ Account Transaction
ConsumptionEvent ≠ Health Food Entry
Merchant         ≠ Travel Place
Receipt          ≠ Asset 本体
Forecast         ≠ 已发生事实
```

## 7. 产品导航

```text
记录：快速录入、本月概览、最近记录、待确认草稿
消费：按场景、商家、内容查看消费历史
计划：想买、想吃、周期事项和到期提醒
洞察：金额趋势、频率、常去商家和常买内容
```

界面不出现“账户、余额、借方、贷方、对账”等传统账本术语。
